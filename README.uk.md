# Сервіс Puppet Forge

> **Операційна карта:** [SCHEMA.uk.md](docs/SCHEMA.uk.md) описує роботу одного й кількох
> екземплярів, межі спільного стану, запобіжники та точкові перевірки кожного
> важливого вузла.

[English version](README.md)

Сервіс на Go для внутрішнього аналога Puppet Forge:

- публікація модулів і версій;
- керування просторами публікації команд;
- доступ команд за токенами та через OIDC;
- проксіювання та кешування офіційного API Puppet Forge;
- зберігання артефактів у GCS або S3-сумісному сховищі;
- зберігання метаданих у SQL-сховищі;
- запуск у Kubernetes.

## Можливості

Поточна реалізація покриває:

- `POST /api/v1/modules` для завантаження нової версії модуля;
- `POST /v3/releases` для JSON/base64 завантаження за контрактом Puppet Forge V3, який використовує PDK 3.4 і новіші версії;
- `GET /v3/modules` і `GET /v3/releases` для об'єднаного каталогу локальних та індексованих upstream-модулів із Forge-сумісними фільтрами й пагінацією;
- `GET /api/v1/manage/publish-spaces` для списку просторів, доступних автентифікованому суб'єкту публікації;
- `GET /api/v1/modules?limit=20&offset=0` для списку модулів; відповідь містить `items`, `limit`, `offset` і `total`;
- `GET /api/v1/modules/{owner}/{name}` для картки модуля;
- `DELETE /api/v1/modules/{owner}/{name}` для видалення модуля з правами глобального адміністратора або адміністратора команди;
- `GET /api/v1/modules/{owner}/{name}/versions/{version}` для конкретного релізу;
- `DELETE /api/v1/modules/{owner}/{name}/versions/{version}` для видалення окремої версії з правами глобального адміністратора або адміністратора команди;
- `GET /api/v1/modules/{owner}/{name}/versions/{version}/download` для завантаження збереженого артефакту через сервіс;
- `GET /` для початкової HTML-сторінки зі списком локально опублікованих модулів;
- `GET /modules/{owner}/{name}` для HTML-сторінки модуля з README у Markdown, вибором версії та інструкціями встановлення;
- `GET /v3/*` і `HEAD /v3/*` для зворотного проксіювання на офіційний API Puppet Forge;
- `/manage` для огляду доступних модулів і команд без дій керування;
- `/manage/modules` для публікації, видалення, пошуку та імпорту модулів із зовнішнього Forge;
- `/manage/teams` для списку доступних команд та окремі сторінки `/access`, `/tokens` і `/modules` для керування вибраною командою;
- `/manage/admin/access` і `/manage/admin/spaces` для структурованої глобальної конфігурації доступу, що зберігається у БД;
- `ADMIN_TOKEN` для початкового та аварійного доступу;
- вхід через OIDC для глобальних адміністраторів, адміністраторів команд і командних груп публікації;
- `PUBLIC_MODULE_ACCESS` для режиму публічного машинозчитуваного доступу та встановлення;
- відстеження активних релізів, яке захищає останні й використовувані версії від випадкового видалення, але залишає адміністраторам явний аудитований override у `/manage/modules`;
- `GET /healthz` і `GET /readyz`.

Поза поточною реалізацією:

- пошук із фільтрами, рейтингами, залежностями й перевіреними видавцями;
- повна API-сумісність з офіційним Puppet Forge;
- CDN і підписані URL з TTL.

## Архітектура

- HTTP API: стандартний `net/http`;
- Рівень сервісу: валідація, оркестрація завантаження та запису метаданих;
- сховище артефактів: GCS або S3-сумісне об'єктне сховище;
- сховище метаданих: `postgres://` або `sqlite://`, яке обирається через `DATABASE_DSN`;
- зовнішній проксі: зворотний проксі на офіційний API Forge з TTL-кешем у пам'яті для JSON-відповідей на GET/HEAD.

Потік публікації:

1. Клієнт надсилає багатокомпонентний запит з архівом tar.gz і, необов'язково, явним `space`.
2. Сервіс автентифікує суб'єкта та читає ідентичність і метадані з архіву.
3. Сервіс перевіряє право суб'єкта публікувати для owner із metadata. Явний `space` має збігатися з цим owner.
4. MD5, SHA-256 і розмір обчислюються один раз. Архів створюється без перезапису за шляхом `modules/<owner>/<name>/<version>/<sha256>.tar.gz`.
5. Публікація через bearer-токен зберігає ідентичність локального релізу незмінною: повторна публікація тих самих байтів є ідемпотентною, а інший вміст для наявної пари модуль/версія повертає `409 Conflict`. Глобальний адміністратор або адміністратор команди-власника може явно вибрати **Replace existing release** в інтерфейсі керування, щоб виправити помилковий архів без вимкнення захисту активних релізів.
6. Метадані релізу створюються в SQL-сховищі й повертаються клієнту. За однозначної помилки збереження незакомічений об'єкт видаляється компенсаційною операцією.

Потік проксіювання:

1. Клієнт викликає маршрут `/v3/...` нашого сервісу.
2. Сервіс надсилає запит на офіційний API Puppet Forge.
3. JSON-відповіді кешуються в пам'яті на `UPSTREAM_PROXY_JSON_CACHE_TTL`.
4. Перший запит файлу за маршрутом `/v3/files/...` запускає його потоковий запис у create-only object під префіксом `upstream-cache/`, після чого сервіс так само потоково віддає завершений shared object без перенаправлення. Повний tar-архів не зберігається в пам'яті proxy.
5. Якщо Forge вже рекламує реліз, але його metadata за маршрутом `/v3/releases/...` ще недоступні, сервіс перевіряє `/v3/files/...tar.gz`, обчислює обидві контрольні суми з артефакту та повертає r10k повну локальну відповідь замість тимчасового metadata 404.
