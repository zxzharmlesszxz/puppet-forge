## Як опублікувати свій модуль

Сервіс приймає `tar.gz` архів Puppet-модуля через `POST /api/v1/modules` як `multipart/form-data`.

Мінімальні вимоги до модуля:

- в архіві має бути рівно один валідний `metadata.json`;
- усі записи архіву мають бути всередині одного канонічного кореневого каталогу `<owner>-<name>-<version>`;
- `metadata.json` і необов'язковий README мають бути безпосередніми дочірніми файлами кореневого каталогу;
- абсолютні шляхи, вихід до батьківських каталогів, посилання, пристрої та інші спеціальні записи tar відхиляються;
- розмір окремого запису й загальний розпакований розмір архіву обмежені;
- `metadata.json.name` має бути у форматі `<owner>-<name>`, наприклад `teamname-apache`;
- `owner` може містити латинські літери в обох регістрах і цифри; коротке ім'я модуля `name` може містити малі латинські літери, цифри та символи підкреслення; дефіс зарезервовано як однозначний розділювач цих частин;
- у `metadata.json.version` має бути версія;
- якщо передано необов'язкове поле `space`, простір імен із `metadata.json.name` має з ним збігатися;
- README бажано покласти в `README.md`, тоді він з'явиться на HTML-сторінці модуля.

Приклад структури:

```text
teamname-apache-1.2.3/
  metadata.json
  README.md
  manifests/
    init.pp
```

Приклад `metadata.json`:

```json
{
  "name": "teamname-apache",
  "version": "1.2.3",
  "summary": "Модуль Apache",
  "author": "Приклад команди"
}
```

Зібрати архів можна стандартним `puppet module build`:

```bash
cd /path/to/teamname-apache
puppet module build
```

Після цього Puppet зазвичай покладе артефакт у `pkg/teamname-apache-1.2.3.tar.gz`.

Для публікації обов'язково передається архів; цільовий простір можна передати явно.

```bash
export FORGE_URL="https://forge.example.com"
export PUBLISH_TOKEN="replace-me"

curl -X POST "${FORGE_URL}/api/v1/modules" \
  -H "Authorization: Bearer ${PUBLISH_TOKEN}" \
  -F "space=teamname" \
  -F "file=@pkg/teamname-apache-1.2.3.tar.gz"
```

Важливо:

- для публікації потрібне поле `file`; поле `space` необов'язкове;
- власник, назва, версія, короткий і повний описи та інші метадані беруться виключно з `metadata.json`;
- задані вручну поля ідентичності або перевизначення метаданих відхиляються;
- якщо `space` передано, простір імен архіву має з ним збігатися;
- authorization завжди перевіряє простір імен архіву з `metadata.json`; токен має мати роль `publish` і давати право на цей простір публікації. У структурованому інтерфейсі простір із назвою `Team` додається автоматично; додаткові простори призначають глобальні адміністратори у `/manage/admin/spaces`;
- багатокомпонентне завантаження, обчислення контрольних сум, запис до об'єктного сховища й завантаження релізу працюють потоково; великий архів не копіюється в один буфер у пам'яті.

PDK 3.4 і новіші версії завжди публікують у `/v3/releases`. Передай базову адресу Forge; сервіс декодує офіційне JSON/base64 тіло запиту, визначить простір із `metadata.json` і застосує ті самі правила авторизації, що й multipart endpoint:

```bash
pdk release publish \
  --forge-token "${PUBLISH_TOKEN}" \
  --forge-upload-url "${FORGE_URL}"
```

Переглянути простори, доступні токену публікації:

```bash
curl "${FORGE_URL}/api/v1/manage/publish-spaces" \
  -H "Authorization: Bearer ${PUBLISH_TOKEN}"
```

Швидка перевірка після публікації:

```bash
curl "${FORGE_URL}/api/v1/modules/teamname/apache"
curl -I "${FORGE_URL}/api/v1/modules/teamname/apache/versions/1.2.3/download"
```

HTML-сторінка модуля буде доступна за адресою:

```text
https://forge.example.com/modules/teamname/apache
```

Вебінтерфейс також містить:

- інтерактивний фільтр на початковій сторінці `/`;
- відтворення README у форматі Markdown, зокрема таблиць із розділювачами `|`; широкі таблиці прокручуються горизонтально всередині README, не розширюючи сторінку;
- випадний список вибору версії модуля;
- готові інструкції встановлення модуля й підключення цього сервісу як власного Forge.

## Спостережуваність

- `puppet_forge_build_info{version,go_version}` містить версію сервісу та Go runtime;
- окремий сервер метрик задається через `METRICS_ADDR` і не маршрутизується через Ingress застосунку;
- журналювання всіх HTTP-запитів;
- метрики Prometheus на `GET /metrics`.
- Інвентарні метрики для модулів:
  - `puppet_forge_modules{owner}`
  - `puppet_forge_module_releases{source}`
  - `puppet_forge_module_latest_releases{source}`
  - `puppet_forge_module_metrics_ready`
  - `puppet_forge_module_metrics_last_success_timestamp_seconds`
  - `puppet_forge_module_metrics_refresh_errors_total`
  - `puppet_forge_module_metrics_owners_total`
  - `puppet_forge_module_metrics_truncated`
- Операційні метрики:
  - `puppet_forge_publish_total{result}`
  - `puppet_forge_delete_total{result,kind}`
  - `puppet_forge_release_usage_mark_total{result}`
  - `puppet_forge_artifact_stream_total{source,result}`
  - `puppet_forge_artifact_stream_bytes_total{source}`
  - `puppet_forge_upstream_sync_total{result,trigger}`
  - `puppet_forge_upstream_refresh_cycles_total{result}`
  - `puppet_forge_upstream_refresh_duration_seconds`
  - `puppet_forge_upstream_refresh_last_duration_seconds`
  - `puppet_forge_upstream_refresh_last_timestamp_seconds`
  - `puppet_forge_upstream_refresh_last_success_timestamp_seconds`
  - `puppet_forge_upstream_refresh_last_error_timestamp_seconds`
  - `puppet_forge_upstream_refresh_modules{result}`
  - `puppet_forge_upstream_cache_requests_total{kind,result}`

Метрики:

- `puppet_forge_modules` експортує кількість модулів, згруповану за обмеженою міткою `owner`;
- `puppet_forge_module_releases` експортує кількість локально доступних релізів, згруповану за міткою `source`;
- `puppet_forge_module_latest_releases` експортує кількість останніх релізів, згруповану за міткою `source`;
- інвентарні метрики рівня релізів навмисно агреговані, щоб `/metrics` залишався швидким навіть за великої кількості версій модулів.

Назви й версії окремих модулів навмисно не експортуються як мітки Prometheus. Для інвентаризації на рівні релізів використовуй API каталогу або вебінтерфейс керування.

Повний опис метрик див. у [METRICS.uk.md](METRICS.uk.md).

## Параметри запуску

Параметри запуску можна передавати через змінні середовища або аргументи командного рядка. Якщо задано обидва варіанти, аргументи командного рядка мають пріоритет.

Бінарний файл виводить версію збірки й завершує роботу за командою:

```bash
puppet-forge --version
```

Назви аргументів утворюються з назв змінних середовища: використовуються малі літери, а символи підкреслення замінюються дефісами:

```text
DATABASE_DSN -> --database-dsn
LOG_LEVEL -> --log-level
MANAGE_SESSION_SECRET -> --manage-session-secret
ACCESS_TOKEN_PEPPER -> --access-token-pepper
TRUSTED_PROXY_CIDRS -> --trusted-proxy-cidrs
TRUST_FORWARDED_HEADERS -> --trust-forwarded-headers
ALLOWED_PUBLIC_HOSTS -> --allowed-public-hosts
README_IMAGE_ALLOWED_HOSTS -> --readme-image-allowed-hosts
PUBLIC_MODULE_ACCESS -> --public-module-access
OIDC_SCOPES -> --oidc-scopes
OIDC_SIGNING_ALGORITHMS -> --oidc-signing-algorithms
UPSTREAM_PROXY_JSON_CACHE_TTL -> --upstream-proxy-json-cache-ttl
UPSTREAM_PROXY_JSON_STALE_TTL -> --upstream-proxy-json-stale-ttl
```

Приклад:

```bash
puppet-forge \
  --database-dsn "postgres://forge:forge@postgres:5432/forge?sslmode=disable" \
  --admin-token "replace-me-bootstrap-token" \
  --artifact-backend s3 \
  --artifact-endpoint "http://seaweedfs:8333" \
  --artifact-bucket "puppet-forge-artifacts" \
  --public-module-access=false
```

## Помилки перевірки ліміту входу

Повідомлення `login rate limit service is unavailable` означає збій спільного
лімітера на базі БД, а не вичерпання кількості спроб. Вхід блокується,
відповідь має статус HTTP 503. Сервер пише `shared rate limit check failed`
із `request_id`, `scope` та початковою помилкою. За нею перевіряй доступність
БД, схему або SQL-запит. Не вимикай лімітер для обходу цієї помилки.

## Зображення та бейджі README

Адміністратор задає дозволені джерела зовнішніх зображень через
`README_IMAGE_ALLOWED_HOSTS`: точні імена вузлів через кому або пробіл.
За замовчуванням дозволено `img.shields.io`, `github.com`, `coveralls.io`,
`s3.amazonaws.com` та `www.puppetmodule.info`. Власний список замінює типовий;
явно заданий порожній рядок вимикає зовнішні зображення. Локальні зображення
з архіву та зображення `data:` залишаються дозволеними.
URL зображень Markdown із `http://` перед відображенням змінюються на `https://`;
список дозволених вузлів залишається чинним. Звичайні посилання не змінюються.

Для Helm задай цей самий параметр у своєму файлі values:

```yaml
config:
  README_IMAGE_ALLOWED_HOSTS: "img.shields.io,github.com,coveralls.io,s3.amazonaws.com,www.puppetmodule.info,badges.example.com"
```

CSP дозволяє лише HTTPS-зображення з цих точних імен вузлів. Піддомени потрібно
додавати окремо; wildcard, схеми, порти, шляхи та CSP-директиви відхиляються
під час запуску. Автор README не може розширювати цей список. Додавай вузол
лише після перевірки URL зображення та довіри до його оператора.

Кінцевий вузол після перенаправлення теж має бути дозволеним. Coveralls
перенаправляє бейджі на `s3.amazonaws.com`, тому одного `coveralls.io`
недостатньо. Хост S3 спільний: цей дозвіл охоплює HTTPS-зображення й з інших
контейнерів на цьому хості, не лише Coveralls. Власний список може не містити
цей хост, якщо такі зображення потрібно блокувати.

Зображення завантажує браузер напряму, без проксіювання через Forge, тому
постачальник бачить IP читача. Заблоковане або недоступне зображення замінюється
підписом `alt`, а без підпису — текстом `Image unavailable`. Якщо зображення
успішно завантажилося й саме містить напис `404 badge not found`, воно
показується як є; виправити потрібно URL бейджа в README модуля.

## Сховища артефактів

- `ARTIFACT_BACKEND=gcs` використовує Google Cloud Storage;
- `ARTIFACT_ENDPOINT` за замовчуванням дорівнює `https://storage.googleapis.com`; якщо його перевизначити, GCS API та URL артефактів використовують цю кінцеву точку без зміни глобальних змінних середовища процесу;
- `ARTIFACT_BUCKET` задає контейнер для артефактів;
- `ARTIFACT_PROJECT` задає проєкт лише тоді, коли ввімкнене створення контейнера під час запуску;
- Для роботи з попередньо створеним контейнером GCS потрібні права створення, читання, видалення та переліку об'єктів, наприклад `roles/storage.objectAdmin` на цей контейнер. `ARTIFACT_ENSURE_BUCKET=true` додатково потребує `storage.buckets.get` і `storage.buckets.create`; для workload identity цей параметр варто лишати вимкненим, якщо сервіс не має створювати контейнер.
- `ARTIFACT_PREFIX` задає префікс сховища для модульних артефактів;
- `ARTIFACT_BACKEND=s3` використовує S3-сумісне об'єктне сховище, зокрема режим сумісності GCS, SeaweedFS або Ceph; backend зобов'язаний атомарно виконувати `If-None-Match: *` для `PutObject`, бо від цього залежить незмінність create-only записів і це перевіряє integration test підтримуваного backend;
- для `s3` треба задати `ARTIFACT_ENDPOINT`, `ARTIFACT_BUCKET`, `ARTIFACT_ACCESS_KEY_ID`, `ARTIFACT_SECRET_ACCESS_KEY`; `ARTIFACT_PATH_STYLE=true` корисний для кінцевих точок GCS і SeaweedFS зі шляховою адресацією;
- `UPSTREAM_SYNC_INTERVAL` вмикає фонове оновлення вже закешованих зовнішніх модулів з офіційного Forge;
- `UPSTREAM_SYNC_LIMIT` обмежує кількість зовнішніх модулів на один цикл оновлення.
- `UPSTREAM_SYNC_CONCURRENCY` обмежує кількість паралельних запитів одного циклу оновлення.

### Автентифікація GCS через service account

Коли задано `ARTIFACT_BACKEND=gcs` і `ARTIFACT_GCS_ANONYMOUS=false`, сервіс
використовує [Application Default Credentials](https://cloud.google.com/docs/authentication/application-default-credentials). У GKE використовуй [Workload Identity Federation for GKE](https://cloud.google.com/kubernetes-engine/docs/how-to/workload-identity), а не довготривалий ключ service account у Kubernetes Secret.

Створи або вибери Google service account і надай йому права лише на об'єкти в
bucket артефактів. Сам bucket зазвичай треба створювати окремо від застосунку:

```bash
export PROJECT_ID="my-gcp-project"
export GSA_NAME="puppet-forge"
export GSA_EMAIL="${GSA_NAME}@${PROJECT_ID}.iam.gserviceaccount.com"
export NAMESPACE="puppet-forge"
export KSA_NAME="puppet-forge"
export BUCKET="puppet-forge-artifacts"

gcloud services enable iamcredentials.googleapis.com --project="${PROJECT_ID}"
gcloud iam service-accounts create "${GSA_NAME}" --project="${PROJECT_ID}"
gcloud storage buckets add-iam-policy-binding "gs://${BUCKET}" \
  --member="serviceAccount:${GSA_EMAIL}" \
  --role="roles/storage.objectAdmin"
gcloud iam service-accounts add-iam-policy-binding "${GSA_EMAIL}" \
  --project="${PROJECT_ID}" \
  --member="serviceAccount:${PROJECT_ID}.svc.id.goog[${NAMESPACE}/${KSA_NAME}]" \
  --role="roles/iam.workloadIdentityUser"
```

Якщо Google service account уже існує, пропусти команду його створення. Суб'єкту,
який додає bucket IAM binding, потрібне право змінювати IAM policy bucket. Самому
Puppet Forge достатньо `roles/storage.objectAdmin` лише на цей bucket: роль
покриває створення, читання, перелік і видалення об'єктів для публікації,
завантаження, звірки та очищення.

Налаштуй чарт на створення Kubernetes ServiceAccount із відповідною назвою та
анотацією GKE:

```yaml
serviceAccount:
  create: true
  name: puppet-forge
  annotations:
    iam.gke.io/gcp-service-account: puppet-forge@my-gcp-project.iam.gserviceaccount.com

config:
  ARTIFACT_BACKEND: gcs
  ARTIFACT_ENDPOINT: https://storage.googleapis.com
  ARTIFACT_BUCKET: puppet-forge-artifacts
  ARTIFACT_PROJECT: my-gcp-project
  ARTIFACT_ENSURE_BUCKET: "false"
  ARTIFACT_GCS_ANONYMOUS: "false"
```

Потрібні одночасно анотація та binding `roles/iam.workloadIdentityUser`. У
стандартному кластері GKE metadata server має бути ввімкнений на кожному node
pool, де можуть запускатися Pod сервісу; GKE Autopilot вмикає Workload Identity
Federation автоматично. Чарт залишає `automountServiceAccountToken=false`, бо
сервіс не звертається до Kubernetes API, а ідентичність GKE надає metadata server.

Після розгортання перевір анотацію Kubernetes ServiceAccount і опублікуй невеликий
модуль через звичайний API або вебінтерфейс. Успішні публікація й завантаження
перевіряють створення та читання об'єктів, а видалення або звірка артефактів —
права переліку й видалення:

```bash
kubectl -n "${NAMESPACE}" get serviceaccount "${KSA_NAME}" -o yaml
kubectl -n "${NAMESPACE}" logs -l app.kubernetes.io/name=puppet-forge --tail=100
```

Поза GKE клієнт використовує стандартний ланцюжок ADC. Перевагу слід надавати
workload identity відповідної платформи. Якщо без JSON-ключа service account не
обійтися, змонтуй його як файл лише для читання і задай
`GOOGLE_APPLICATION_CREDENTIALS` із цим шляхом через механізм ін'єкції секретів
платформи. Helm-чарт навмисно не створює і не зберігає довготривалі ключі Google
service account.

## Сховище бази даних

- `DATABASE_DSN=postgres://...` вмикає PostgreSQL;
- `DATABASE_DSN=sqlite:///data/puppet-forge.db` вмикає SQLite;
- тип бази даних визначається схемою DSN, тому окремий `DB_BACKEND` не потрібен;
- PostgreSQL призначений для промислового розгортання з кількома репліками. SQLite підходить для локального розгортання з одним процесом запису; оренда оновлення там спирається на блокування транзакцій SQLite, а не на PostgreSQL `FOR UPDATE NOWAIT`.

## Керування доступом

- конфігурація доступів зберігається тільки в БД: `access_teams`, `access_tokens`, `access_publish_owners`, `access_oidc_mappings`;
- `ACCESS_JSON` більше не використовується;
- `ADMIN_TOKEN` — початковий та аварійний токен середовища виконання, який не записується в БД;
- токени доступу генеруються як непрозорі облікові дані, показуються лише один раз і зберігаються як HMAC-SHA256-відбиток із видимим префіксом та метаданими життєвого циклу; кожен новий токен має обов'язкову зрозумілу назву та роль `read` або `publish`, а активна пара назви й ролі має бути унікальною в межах команди; `ACCESS_TOKEN_PEPPER` має бути однаковим на всіх репліках; кожен захищений bearer-запит перевіряє активність token ID у SQL, тому відкликання та завершення строку дії застосовуються на всіх репліках одразу після commit; сторінка керування має одну форму створення та незалежну пагінацію списку активних токенів і неактивної історії: початково по 20 записів із запам'ятовуваним вибором 10, 20, 50 або 100; `ACCESS_TOKEN_HISTORY_TTL` видаляє старі метадані прострочених і відкликаних токенів;
- якщо БД не містить жодних чинних облікових даних доступу і `ADMIN_TOKEN` не заданий, сервіс не стартує;
- під час чистого старту увійди в `/manage` через `ADMIN_TOKEN`, відкрий `/manage/teams` і налаштуй команди, токени, групи OIDC та адміністраторів команд OIDC; додаткові простори публікації призначають глобальні адміністратори у `/manage/admin/spaces`, а глобальні зіставлення OIDC налаштовуються у `/manage/admin/access`;
- кожне значення токена має бути глобально унікальним для всіх команд і ролей доступу; повторне використання токена читання, публікації або адміністратора відхиляється без виведення самого токена в помилці;
- `platform-admin` є зарезервованим ідентифікатором конфігурації для токенів глобального адміністратора та зіставлень OIDC; його не можна створити або використати як команду публікації чи простір модулів;
- назви команд публікації та додаткових writable-просторів мають відповідати синтаксису owner модуля `[A-Za-z0-9]+`; назви команд також мають бути унікальними без урахування регістру;
- вебінтерфейс (`/` і `/modules/...`) лишається відкритим для інформаційного перегляду локальних модулів незалежно від `PUBLIC_MODULE_ACCESS`;
- токени читання дають доступ до API читання, завантаження та `/v3/*`;
- токени публікації дають доступ до читання та незмінної публікації лише в дозволених просторах, але не можуть замінювати наявну версію чи видаляти модулі;
- глобальні адміністратори можуть замінити наявний локальний реліз у будь-якому writable-просторі, а адміністратори команд — лише в основному просторі керованої команди; заміна завантажує новий content-addressed object, атомарно перемикає SQL-метадані та ставить попередній object у надійну чергу видалення; клієнтам із закешованою попередньою checksum може знадобитися повторний запит;
- глобальні адміністратори призначають і відкликають `Extra publish spaces` у `/manage/admin/spaces`; ці простори дозволяють публікацію та оновлення, але не надають права видалення; глобальні адміністратори можуть видаляти модулі та версії в будь-якому просторі імен, а адміністратори команд OIDC — лише в основному просторі своєї команди;
- зіставлення адміністраторів команд OIDC дають доступ до редагування токенів і груп OIDC тільки своєї команди;
- зіставлення глобальних адміністраторів OIDC дають повний доступ до адміністративних маршрутів (`/manage/admin/*`) і видалення модулів або версій у будь-якому просторі імен;
- `PUBLIC_MODULE_ACCESS=false` вимагає токен читання, публікації або адміністратора для маршрутів встановлення й API: читання API, завантаження релізів, видобутих файлів модулів і `/v3/*`;
- `PUBLIC_MODULE_ACCESS=true` відкриває ці маршрути без токена, щоб r10k і `puppet module install` могли забирати модулі без заголовка Authorization;
- `PUBLIC_MODULE_ACCESS=true` не відкриває публікацію, видалення, `/manage` або `/manage/admin/*`.

## Вебавтентифікація та OIDC

- `WEB_AUTH_MODE=oidc` вмикає вхід із сесією для вебінтерфейсу через OIDC/Authentik;
- API при цьому й надалі використовує токени команд;
- потрібні `OIDC_ISSUER_URL`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `OIDC_COOKIE_SECRET`;
- стан авторизації одноразовий і живе п'ять хвилин; потік використовує прив'язку nonce, PKCE S256, строгі перевірки видавця, аудиторії, підпису й строку дії та список дозволених `OIDC_SIGNING_ALGORITHMS`;
- браузер отримує лише непрозорий ідентифікатор OIDC-сесії; атрибути ідентичності, прив'язаний до сесії секрет CSRF, строк дії, час останньої активності й стан відкликання зберігаються в SQL, а вихід відкликає спільний запис сесії;
- `OIDC_SCOPES` за замовчуванням дорівнює `openid profile email`; додай `groups`, якщо постачальник повертає твердження про групи лише з цією областю доступу;
- `OIDC_REDIRECT_URL` можна задати явно, але зазвичай краще лишити порожнім: сервіс побудує URL перенаправлення з імені вузла й протоколу поточного запиту та додасть `/auth/callback`;
- `PUBLIC_BASE_URL` не обов'язковий і використовується лише як резервне значення. За замовчуванням береться `Host` запиту, тому кілька імен Ingress працюють без канонічного URL;
- передані проксі ім'я вузла й протокол ігноруються, якщо одночасно не задані `TRUST_FORWARDED_HEADERS=true` та відповідний `TRUSTED_PROXY_CIDRS`; за завершення HTTPS на Ingress налаштуй обидва параметри. `ALLOWED_PUBLIC_HOSTS` використовуй для фіксованого набору імен; залишай його порожнім лише тоді, коли маршрутизація Ingress і політика перенаправлень постачальника ідентичності обмежують контрольовану динамічну DNS-зону;
- у Kubernetes Ingress має передавати справжній `Host` і схему через `X-Forwarded-Host`/`X-Forwarded-Proto` або RFC `Forwarded`;
- для командного вебінтерфейсу користувачі OIDC зіставляються з командами через `oidc_groups`;
- для делегованого доступу адміністратора команди OIDC-користувачі зіставляються через `oidc_team_admin_emails` або `oidc_team_admin_groups`.

## Вебінтерфейс керування

- `/manage` відкриває огляд доступних модулів і команд без форм керування;
- `/manage/modules` відкриває загальну сторінку публікації, пошуку та видалення модулів;
- `/manage/teams` показує тільки доступні користувачу команди, а `/manage/teams/{team}/access`, `/tokens` і `/modules` розділяють налаштування доступу, токени та модулі вибраної команди;
- публічні й Manage-списки з пагінацією оновлюють через progressive HTML fragment-запити лише власні рядки, лічильники та елементи керування; фільтри й browser history працюють через той самий механізм, звичайна навігація лишається fallback, а розмір сторінки запам'ятовується з вибором 10, 20, 50 або 100 елементів;
- `/manage/admin/access` доступний глобальним адміністраторам для керування глобальними зіставленнями OIDC;
- `/manage/admin/spaces` доступний лише глобальним адміністраторам для призначення додаткових просторів публікації командам і відкликання цих призначень; основний простір із назвою команди створюється автоматично й не відкликається;
- адміністратори команд керують токенами та OIDC-відповідностями своєї команди на окремих сторінках `/manage/teams/{team}/tokens` і `/access`;
- адміністратори команд не можуть перейменовувати або видаляти команди, змінювати `Extra publish spaces`, редагувати глобальних адміністраторів чи змінювати чужі команди;
- головна сторінка керування має назву `Overview`, а глобальна навігація окремо містить `Modules` і `Teams`;
- якщо `WEB_AUTH_MODE=oidc`, `/manage` використовує вхід через OIDC і права з БД;
- без OIDC або як резервний варіант можна увійти через наявний токен із роллю `publish` із БД або через стартовий `ADMIN_TOKEN`;
- ідентичність OIDC або токен публікації бачить і змінює тільки простір із назвою `Team` та додаткові простори з `Extra publish spaces`;
- токен публікації не може видаляти модулі або версії;
- адміністратор команди через OIDC може видаляти модулі й версії тільки в основному просторі своєї команди;
- `ADMIN_TOKEN` або адміністративне зіставлення OIDC можуть видаляти модулі й версії в будь-якому просторі імен;
- версії, які завантажували r10k або `puppet module install` протягом `ACTIVE_RELEASE_TTL`, позначаються як `in use`, а звичайне видалення їх відхиляє;
- адміністратор команди-власника або глобальний адміністратор може примусово видалити активний чи останній реліз через окрему сторінку після введення причини та точного підтвердження `owner/name@version`; після цього CI може повторно опублікувати виправлений архів із тією самою версією;
- примусово видалити весь модуль може лише глобальний адміністратор через окрему сторінку після введення причини й точного підтвердження `owner/name`;
- HTTP API приймає той самий override через заголовки `X-Puppet-Forge-Force-Delete: true`, `X-Puppet-Forge-Delete-Reason` і `X-Puppet-Forge-Delete-Confirmation`;
- адміністративні зміни команд, доступів, токенів, publish spaces, модулів і релізів створюють structured-події `security_audit` одночасно в application logs і SQL-журналі `/manage/admin/audit`; глобальна сторінка показує повний журнал, а `/manage/teams/{team}/audit` на backend обмежує його командою та її publish spaces і включає дії глобальних адміністраторів над цими ресурсами; обидві сторінки підтримують фільтрацію та пагінацію і зберігають коментар примусового видалення разом із виконавцем, source address, ресурсом, результатом і request ID; централізований logging backend має зберігати дубльований потік для незалежного зіставлення операцій;
- після видалення останнього релізу система автоматично призначає latest найвищу з наявних semantic versions; якщо релізів не лишилося, запис модуля видаляється;
- `ACTIVE_RELEASE_TTL` за замовчуванням дорівнює `720h` / 30 днів і задається при старті сервісу;
- записи використання, старші за активне вікно, очищує щоденний worker під спільною SQL lease; перший асинхронний цикл запускається одразу після старту;
- перевірка політики та зміна SQL виконуються під одним module lock між репліками; транзакція видаляє metadata й додає кожен локальний object path у надійний `artifact_deletions` outbox. Singleton worker щохвилини повторює idempotent видалення зі сховища. Помилка сховища залишає лише object і завдання outbox, але не metadata, що посилаються на відсутній архів. Перед cleanup повторна публікація перевіряється під тим самим module lock;
- видалення метаданих індексованого зовнішнього релізу не додає спільний об'єкт із `upstream-cache/` до негайного видалення; щоденний worker, обраний через lease, прибирає лише об'єкти без SQL-посилань, старші за `UPSTREAM_ARTIFACT_ORPHAN_TTL`;
- видалені зовнішні версії записуються в таблицю позначок `deleted_releases`, тому фонова синхронізація не відновлює їх одразу; прямий запит саме цього релізу від r10k, Puppet або іншого клієнта навмисно відновлює його на вимогу, щоб старі середовища залишалися придатними до розгортання без фонового повернення всіх видалених версій; `DELETED_RELEASE_TTL` визначає строк фонового блокування, після якого реліз може повернути й синхронізація;
- видалення всього модуля очищає позначки видалення та дані використання релізів, тому після повторної синхронізації модуль можна створити заново з усіма доступними зовнішніми релізами;
- форма завантаження використовує ті самі правила, що й `POST /api/v1/modules`: користувач вибирає дозволений простір і файл, а ідентичність та метадані беруться з `metadata.json`.

Налаштуй OIDC через runtime-змінні середовища або відповідні аргументи командного
рядка:

```bash
export WEB_AUTH_MODE=oidc
export PUBLIC_MODULE_ACCESS="false"
export OIDC_ISSUER_URL="https://auth.example.com/application/o/puppet-forge/"
export OIDC_CLIENT_ID="puppet-forge"
export OIDC_CLIENT_SECRET="replace-me"
export OIDC_COOKIE_SECRET="32-byte-random-secret"
# Необов'язково: якщо виявлення не повертає `end_session_endpoint`.
export OIDC_LOGOUT_URL="https://auth.example.com/application/o/puppet-forge/end-session/"
export ADMIN_TOKEN="replace-with-at-least-32-random-bytes"
export ACCESS_TOKEN_PEPPER="replace-with-at-least-32-random-bytes"
export MANAGE_SESSION_SECRET="replace-with-a-different-32-byte-secret"
```

У постачальнику ідентифікації треба додати точний публічний URI перенаправлення:

```text
https://forge.example.com/auth/callback
```

Для динамічних імен Ingress залиш обидва перевизначення URL порожніми й довіряй лише мережам безпосереднього Ingress або зворотного проксі:

```yaml
config:
  PUBLIC_BASE_URL: ""
  OIDC_REDIRECT_URL: ""
  TRUST_FORWARDED_HEADERS: "true"
  TRUSTED_PROXY_CIDRS: "10.0.0.0/8,2001:db8:1234::/48"
  ALLOWED_PUBLIC_HOSTS: ""
```

Тоді сервіс будує `https://<поточне-ім'я-ingress>/auth/callback` із перевіреного запиту. В Authentik додай один Redirect URI з режимом зіставлення **Regex**, прив'язаний до контрольованої DNS-зони замість переліку всіх Ingress:

```regex
^https://(?:[a-z0-9](?:[a-z0-9-]*[a-z0-9])?\.)+example\.com/auth/callback$
```

Не використовуй `.*` або інший необмежений вираз перенаправлення. Authentik описує строгий і regex-режими в [налаштуванні постачальника OAuth2](https://docs.goauthentik.io/add-secure-apps/providers/oauth2/). Значення `TRUSTED_PROXY_CIDRS="0.0.0.0/0,::/0"` можна тимчасово використати для діагностики невідомої мережі проксі, але воно дозволяє кожному безпосередньому клієнту передавати проксі-заголовки ідентичності та джерела; перед промисловим використанням заміни його справжніми CIDR безпосереднього проксі й обмеж прямий доступ до pod.

Вихід із `/manage` відкликає збережену в SQL сесію токена або OIDC та очищає локальні файли cookie. Якщо виявлення OIDC повертає `end_session_endpoint` або задано `OIDC_LOGOUT_URL`, сервіс також спрямовує браузер на вихід у постачальника, щоб Authentik не виконав автоматичний повторний вхід зі старої сесії.

Обмеження частоти входу й публікації зберігаються в обмеженій пам'яті окремо в кожній репліці. Завершені лічильники клієнтів видаляються за допомогою черги пріоритетів; при досягненні межі витісняється лічильник із найближчим часом скидання, щоб нові клієнти не втрачали доступ до сервісу. `TRUSTED_PROXY_CIDRS` дає змогу розрізняти клієнтів за довіреним Ingress; залишай параметр порожнім, якщо CIDR проксі невідомі. Для строгого спільного або стійкого до зловмисної ротації адрес обмеження додатково налаштуй у спільному обмежувачі на Ingress або шлюзі API.

Для групи користувачів краще зіставляти не адреси електронної пошти, а групу OIDC:

```json
{
  "team": "teamname",
  "oidc_groups": ["teamname-devops"]
}
```

В Authentik треба додати користувачів до групи `teamname-devops` і переконатися, що застосунок або постачальник повертає атрибут `groups` в ID-токені. Для командного доступу у вебінтерфейсі використовується саме `oidc_groups`: одна група OIDC дає команді доступ до публікації в просторі з назвою `Team`. Якщо треба дозволити інші простори, глобальний адміністратор призначає їх у `/manage/admin/spaces`. Якщо після входу зіставлення не спрацює, сервіс запише `email`, `subject`, `domain` і `groups` у повідомленні `oidc session is not mapped to team`.

Щоб команда сама керувала своїми токенами й групами OIDC, додай адміністраторів команди в полі `OIDC team admins`. Для однієї-двох людей зручніше використовувати адреси електронної пошти; коли список зростає, краще перейти на групу:

```json
{
  "team": "teamname",
  "oidc_groups": ["teamname-devops"],
  "oidc_team_admin_emails": ["owner@example.com"],
  "oidc_team_admin_groups": ["teamname-admins"]
}
```

Користувач з адресою `owner@example.com` або з групи `teamname-admins` може відкрити `/manage/teams` та окремі сторінки Access, Tokens і Modules для `teamname`. Він не зможе змінити інші команди, глобальних адміністраторів, конфігурацію JSON або додаткові простори публікації. Такий адміністратор може видаляти модулі й версії лише в основному просторі своєї команди. `Extra publish spaces` дають право публікації та оновлення, але видаляти в них може лише глобальний адміністратор.

Одну адресу або групу адміністратора команди OIDC можна додати до кількох команд. Тоді користувач побачить і зможе редагувати всі ці команди в `/manage/teams`, але не матиме доступу до чужих команд або налаштувань глобальних адміністраторів.

Адміністративний OIDC-доступ задається у блоці `Global OIDC Admins`, щоб не змішувати командні групи публікації з глобальними правами:

```json
{
  "team": "platform-admin",
  "oidc_admin_groups": ["forge-admins"]
}
```

Користувач із групи `forge-admins` може відкривати `/manage/admin/access` і видаляти модулі й версії в будь-якому просторі імен. Публікація через адміністративну групу автоматично не вмикається.

Якщо користувач OIDC одночасно входить до командної групи, наприклад `teamname-devops`, і має адміністративне зіставлення через `oidc_admin_groups`, `oidc_admin_emails` або `oidc_admin_subjects`, сервіс об'єднує обидва набори прав. Доступ глобального адміністратора не прибирає командну публікацію або керування командою.

Щоб додати себе як адміністратора після першого запуску:

1. Увійди в `/manage` через `ADMIN_TOKEN`.
2. Відкрий `/manage/admin/access`.
3. У `Global OIDC Admins` додай свою адресу електронної пошти в `OIDC admin emails` або свою групу в `OIDC admin groups`.
4. Збережи глобальних адміністраторів і перелогінься через OIDC.

`ADMIN_TOKEN` варто залишати тільки для початкового або аварійного доступу, наприклад коли OIDC не працює. Для щоденного доступу використовуй групи або адреси електронної пошти адміністраторів OIDC у полях `OIDC admin groups` чи `OIDC admin emails`.

Створюй і редагуй команди на сторінці `/manage/teams`, призначай додаткові простори публікації на сторінці `/manage/admin/spaces`, а глобальних адміністраторів OIDC налаштовуй на сторінці `/manage/admin/access`. Сервіс навмисно не має endpoint для повної заміни конфігурації у форматі JSON. Токени доступу створюй, ротуй і відкликай на сторінці `/manage/teams/{team}/tokens`; початкове значення нового токена показується лише один раз.

Під час оновлення бази зі старою колонкою відкритого тексту `access_tokens.token` сервіс при старті переносить облікові дані до HMAC-схеми. Задай і збережи `ACCESS_TOKEN_PEPPER` до першого запуску оновленої версії: наявні початкові токени продовжать працювати, але втрата або зміна цього секрету зробить їх недійсними.

Helm-чарт також підтримує ресурси Prometheus Operator, але за замовчуванням вони вимкнені:

- `serviceMonitor.enabled=true` створює `ServiceMonitor`, який вибирає внутрішній сервіс лише для метрик;
- `prometheusRule.enabled=true` створює `PrometheusRule` із тими самими правилами запису й оповіщення, що й [examples/prometheus/alerts/puppet-forge.yml](../examples/prometheus/alerts/puppet-forge.yml). Робочі пороги можна налаштувати в `prometheusRule.thresholds`; типові значення відповідають окремому прикладу.

## Kubernetes

Релізний Helm-чарт публікується в
`https://zxzharmlesszxz.github.io/puppet-forge`. Додай репозиторій і встанови
конкретну версію чарту:

```bash
helm repo add puppet-forge https://zxzharmlesszxz.github.io/puppet-forge
helm repo update puppet-forge
helm upgrade --install puppet-forge puppet-forge/puppet-forge \
  --namespace puppet-forge \
  --create-namespace \
  --version X.Y.Z \
  -f my-values.yaml \
  --set secret.existingSecret=puppet-forge-runtime
```

Заміни `X.Y.Z` на опубліковану версію чарту. Фіксація версії робить розгортання
відтворюваним, а оновлення — явним. Код чарту лишається в
[`deploy/puppet-forge`](../deploy/puppet-forge) для розробки та рев'ю, але production
інсталяції мають використовувати опублікований репозиторій.

Створи `my-values.yaml` на основі профілю вибраного artifact backend:

- native Google Cloud Storage: [values-gcs.yaml](../deploy/puppet-forge/values-gcs.yaml);
- S3-сумісне сховище: [values-s3.yaml](../deploy/puppet-forge/values-s3.yaml).

Задай реальні bucket, endpoint, project і режим адресації у deployment values.
Credentials зберігай у `secret.existingSecret`, а не у values під контролем версій.

Чарт вимагає рівно один режим секретів: або задай `secret.existingSecret`, або явно
встанови `secret.create=true` і передай обов'язкові значення. За замовчуванням чарт
не створює облікових даних. Створи вказаний Secret через менеджера секретів або
контролер GitOps щонайменше з `DATABASE_DSN`, `ACCESS_TOKEN_PEPPER` та окремим
`MANAGE_SESSION_SECRET`; додай облікові дані сховища артефактів та OIDC, потрібні
конкретній конфігурації.

Коли зовнішній менеджер оновлює цей Secret без зміни Deployment manifest, задай у `secret.rolloutChecksum` версію або digest зовнішнього Secret. Зміна значення оновить pod template і запустить контрольований rollout.

За замовчуванням чарт використовує фіксований `replicaCount`. Щоб кількістю
реплік керував Kubernetes, задай `autoscaling.enabled: true`, `minReplicas` і
`maxReplicas` у `my-values.yaml`.

Коли `autoscaling.enabled=true`, Deployment не створює `spec.replicas`; цим керує `HorizontalPodAutoscaler`. Не вмикай автоматичне масштабування з `sqlite://` у `DATABASE_DSN`; для кількох реплік потрібні PostgreSQL та однакові `ACCESS_TOKEN_PEPPER` і `MANAGE_SESSION_SECRET` на всіх репліках.

Образ і чарт явно запускають контейнер із числовими UID/GID `10001:10001`, кореневою файловою системою лише для читання, профілем seccomp `RuntimeDefault`, без можливостей Linux і з `emptyDir` у `/tmp`. Числова ідентичність дає kubelet змогу перевірити `runAsNonRoot`, не звертаючись до бази користувачів образу. Монтування токена службового облікового запису за замовчуванням вимкнене. PDB та розподіл за топологією ввімкнені; `networkPolicy.enabled` лишається вимкненим, доки явно не задано дозволених вузлів через `networkPolicy.ingress` і `networkPolicy.egress`.

Ресурси Prometheus Operator вимкнені за замовчуванням. Для збирання метрик і оповіщень увімкни `serviceMonitor.enabled=true` та `prometheusRule.enabled=true`.
