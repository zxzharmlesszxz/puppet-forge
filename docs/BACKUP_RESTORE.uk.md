# Резервне копіювання, відновлення та звірка артефактів

[English version](BACKUP_RESTORE.md)

> **Карта стану та відмов:** [SCHEMA.uk.md](SCHEMA.uk.md) визначає всі межі
> довговічного й локального для процесу стану, механізми координації кількох
> екземплярів і точки перевірки, що використовуються цією процедурою відновлення.

Резервну копію бази метаданих і сховища артефактів потрібно створювати як один
узгоджений комплект відновлення. Також збережіть конфігурацію розгортання та
окремі секретні значення `ACCESS_TOKEN_PEPPER`, `MANAGE_SESSION_SECRET`,
`OIDC_COOKIE_SECRET`, облікові дані клієнта OIDC, доступ до сховища й початковий
`ADMIN_TOKEN`, якщо він використовується. Втрата або зміна цих секретів робить
збережені хеші токенів чи браузерні сесії недійсними.

## Резервне копіювання

1. Для послідовного резервування бази й бакета зупиніть усі репліки Forge та
   окремі завдання зміни даних/repair. Дочекайтеся завершення активних запитів
   і воркерів та не допускайте автоматичного запуску до завершення обох копій.
   Паузи лише публікації та видалення недостатньо: Clear cache, фонові
   refresh/cleanup і наповнення upstream-кешу за клієнтськими запитами можуть
   змінювати SQL або сховище. Альтернатива — узгоджена процедура snapshots бази
   та сховища, яка гарантує єдину точку відновлення. Два незалежні знімки
   працюючих систем такої гарантії не дають.
2. Збережіть PostgreSQL через механізм знімків платформи або командою
   `pg_dump --format=custom`. Для SQLite зупиніть єдиний процес запису й
   скопіюйте файл бази або скористайтеся online backup API SQLite.
   Резервна копія бази містить надійний outbox `artifact_deletions`, тому
   незавершене очищення об'єктів автоматично продовжиться після відновлення та
   запуску сервісу. Вона також містить збережену історію `release_consumers` для
   Grafana legacy usage; звичайне очищення за `RELEASE_CONSUMER_TTL`
   продовжиться після запуску.
3. Створіть знімок або версійну копію всього налаштованого бакета. Щонайменше
   збережіть простір локальних релізів під `ARTIFACT_PREFIX` і незалежний
   `upstream-cache/`, на який посилаються індексовані upstream-релізи.
4. Експортуйте фактичну несекретну конфігурацію, а потрібні секрети збережіть у
   системі резервування секретів організації.
5. Зафіксуйте версію застосунку та переконайтеся, що резервування бази й
   об'єктного сховища завершилося успішно, перш ніж запускати репліки чи
   відновлювати завдання зміни даних.

## Відновлення

1. Залиште сервіс масштабованим до нуля та заблокуйте publish-трафік.
2. Спочатку відновіть об'єктне сховище з того самого комплекту, включно з
   простором локальних релізів під `ARTIFACT_PREFIX` і `upstream-cache/`.
3. Відновіть метадані PostgreSQL або SQLite з відповідного комплекту.
   Не видаляйте відновлені записи `artifact_deletions` вручну. Singleton worker
   перед видаленням ще раз звіряє кожен object path з актуальними metadata
   релізів і повторює операцію після тимчасових помилок сховища.
4. Поверніть початкові секрети хешування, сесій та OIDC і runtime-конфігурацію.
5. До запуску сервісу виконайте звірку в режимі звіту:

   ```bash
   puppet-forge --reconcile-artifacts
   ```

   Команда завершується з ненульовим кодом, якщо знаходить відсутні об'єкти,
   розбіжності checksum/розміру або orphan-об'єкти. JSON-звіт можна зберегти
   разом із протоколом відновлення.

   Reconciliation перевіряє існування, розмір і checksum усіх непорожніх
   `storage_path`, зареєстрованих у SQL, включно з upstream-архівами. Пошук
   orphan-об'єктів сканує лише налаштований `ARTIFACT_PREFIX` (типово `modules/`).
   Він не знаходить незареєстровані об'єкти в окремому `upstream-cache/`.
   Після запуску ними займається щоденний upstream cleanup worker під SQL lease,
   з урахуванням `UPSTREAM_ARTIFACT_ORPHAN_TTL` і поточних посилань. Чистий звіт
   не доводить відсутності orphan-об'єктів у всьому бакеті.

6. Відновіть відсутні або пошкоджені артефакти з резервної копії. Не видаляйте
   їхні SQL-метадані автоматично.
7. Для видалення придатних orphan-артефактів під `ARTIFACT_PREFIX` запустіть
   явний режим repair:

   ```bash
   puppet-forge --reconcile-artifacts --reconcile-repair
   ```

   Repair-режим видаляє лише знайдені orphan-об'єкти з розпізнаним шляхом
   артефакту під цим префіксом; невідомі шляхи потребують розгляду оператором.
   Перед кожним видаленням він бере відповідний module lock, повторно перевіряє
   актуальні SQL-посилання та пропускає об'єкти, створені або змінені після
   початку сканування. Паралельна публікація не може перетворити застарілий звіт
   на видалення чинного артефакту. Repair не видаляє метадані релізів, не замінює
   пошкоджені артефакти й не очищує orphan-об'єкти поза налаштованим префіксом.
8. Повторюйте режим звіту до чистого результату. Потім запустіть один екземпляр,
   перевірте `/readyz`, завантаження, OIDC/token login і publish/delete. Лише
   після цього відновлюйте звичайну кількість реплік.

## Тест аварійного відновлення

Періодично перевіряйте всю процедуру в ізольованому середовищі. Резервна копія
не вважається придатною, доки базу, артефакти, секрети, звірку та вибіркові
завантаження модулів не буде успішно відновлено.
